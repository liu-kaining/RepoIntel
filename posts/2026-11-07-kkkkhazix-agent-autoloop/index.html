解决的工程痛点

开发者用Claude Code/Codex时需实时盯终端，关窗即中断；多项目定时任务需人工逐个触发；Agent自作主张改数据有风险，缺乏可靠的确认机制。

⚙

CTO 级技术审计

从 cli/main.ts 的命令分发到 hub client（protocol/client.ts 被调用）实现事件、回答、状态查询；规则解析在 cli/explain.ts 中调用 protocol/rules.ts 和 kernel/cron.ts 完成；备份恢复在 cli/backup.ts 中直接操作 SQLite；Windows 服务通过 host/background.js 循环拉起 hub。

测试体系健全。.github/workflows/check.yml 定义三OS矩阵和分级 scope；sim/crash.test.ts 执行1000次 SIGKILL 恢复测试；sim/mutation.test.ts 做变异测试，确保内核保护机制有效。

备份恢复工程化。cli/backup.ts 使用 node:sqlite 的 backup API 进行在线备份，restore 前检测 inUse 避免锁冲突，失败时回滚所有替换文件。

未审阅到 kernel/、protocol/、worker/ 目录的核心实现源码（提供的 code_bundle 仅含 kernel/errors.ts），对调度、事务、并发、Agent 适配的具体实现无法确认，只能基于 CLI 调用和测试推断。

插件加载仅校验名字格式（host/plugins.ts），对插件代码无静态分析或签名校验，且未提供插件开发文档源码，自定义插件可能引入安全风险。

先获取完整源码审计 kernel 再用于生产；关注 Node 24 和 git 依赖；从示例 recipes 开始小范围试点。

⚠

隐藏风险与雷点

  • 项目仅创建4天，API与协议可能快速变动，生产使用需锁定版本。
  • 未审阅核心kernel，调度与持久化机制需自行审计后部署。
  • 仅支持Node 24+和已登录Agent，环境门槛较高。
◈

生态与商业价值

个人开发者或小团队可低成本获得自动化中台；但需自行维护，托管服务或企业支持可能成为后续商业化方向。
